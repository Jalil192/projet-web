RÔLE : Déclarer les bibliothèques dont le serveur a besoin.

Ce fichier est le "carnet d'adresses" des dépendances du projet serveur.
Quand on lance "npm install", npm lit ce fichier et télécharge toutes les
bibliothèques listées dans "dependencies".

POURQUOI CES DÉPENDANCES :
  - "express"         → Sans Express, on devrait écrire du Node.js pur pour
                        gérer chaque requête HTTP manuellement. Express simplifie
                        énormément la création de routes et de middlewares.
  - "express-session" → Gère automatiquement les cookies de session. Sans elle,
                        il faudrait implémenter la gestion de session à la main.
  - "cors"            → Bloque par défaut les requêtes d'une origine différente.
                        On doit l'autoriser explicitement entre port 5173 et 3000.
  - "mongodb"         → Le driver officiel pour parler à MongoDB depuis Node.js.
                        Le cours interdit Mongoose, donc on utilise ce driver natif.
  - "bcrypt"          → Un standard de l'industrie pour hasher les mots de passe.
                        On ne peut JAMAIS stocker les mots de passe en clair.
  - "nodemon" (dev)   → Outil de développement qui surveille les fichiers et
                        redémarre le serveur automatiquement après chaque sauvegarde.
                        Évite de relancer "node server.js" à la main à chaque fois.

Les scripts "start" et "dev" définissent ce que font "npm start" et "npm run dev".

RÔLE : Point d'entrée du serveur. Configure tout et démarre l'écoute.

C'est le fichier racine du serveur. Il est le premier à s'exécuter quand
on lance "npm run dev". Il assemble toutes les pièces du serveur.

CE QU'IL FAIT CONCRÈTEMENT :

  1) Importe et configure Express :
     const app = express() → crée l'application serveur

  2) Configure CORS :
     app.use(cors({ origin: 'http://localhost:5173', credentials: true }))
     → Autorise uniquement le client React (port 5173) à contacter ce serveur
     → "credentials: true" est indispensable pour que les cookies de session
       soient transmis avec les requêtes Axios

  3) Configure les parseurs :
     app.use(express.json()) → lit le corps JSON des requêtes
     app.use(express.urlencoded()) → lit les formulaires HTML

  4) Configure les sessions :
     app.use(session({ secret: '...', resave: false, saveUninitialized: false }))
     → "secret" : clé secrète pour signer les cookies (à garder privée en prod)
     → "resave: false" : ne re-sauvegarde pas la session si elle n'a pas changé
     → "saveUninitialized: false" : ne crée pas de session vide
     → "maxAge: 24h" : la session expire après 24 heures

  5) Monte les routeurs sur leurs préfixes :
     app.use('/api/auth', authRouter)     → toutes les routes auth commencent par /api/auth
     app.use('/api/messages', messagesRouter)
     app.use('/api/users', usersRouter)

  6) Route 404 pour les URL inconnues

  7) Fonction async start() :
     → Se connecte d'abord à MongoDB (await connectDB())
     → Peuple si vide (await populateDB())
     → Puis seulement commence à écouter (app.listen(3000))
     → Si MongoDB est indisponible, le serveur s'arrête (process.exit(1))

RÔLE : Gérer la connexion à MongoDB et la partager dans tout le serveur.

PROBLÈME RÉSOLU : On ne veut pas se connecter à MongoDB à chaque requête
(ce serait très lent). On se connecte une seule fois au démarrage et on
réutilise cette connexion.

PATTERN UTILISÉ ("module singleton") :
  - Les variables "client" et "db" sont déclarées au niveau du module
  - connectDB() les initialise une seule fois
  - getDB() les retourne à chaque appel
  - Comme Node.js met en cache les modules, getDB() retourne toujours
    la même instance de connexion

POURQUOI SÉPARER CE FICHIER DU RESTE :
  Chaque fichier de route (auth.js, messages.js, users.js) a besoin
  d'accéder à la base. Plutôt que de dupliquer le code de connexion partout,
  on centralise ici et chacun importe getDB().

GARDE-FOU IMPORTANT :
  La première ligne vérifie si la base est déjà peuplée :
    const usersCount = await db.collection('users').countDocuments();
    if (usersCount > 0) return; // Ne peuple pas deux fois

  Sans ça, chaque redémarrage du serveur créerait des doublons.

BCRYPT POUR LES MOTS DE PASSE :
  Chaque mot de passe est hashé avant insertion :
    const hash = await bcrypt.hash('admin123', 10);
  Le "10" signifie 2^10 = 1024 calculs → rend les attaques par force brute
  très coûteuses en temps.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

RÔLE : Gérer tout ce qui concerne l'authentification des utilisateurs.

Ce fichier contient 4 routes cruciales pour la sécurité du site :

POST /api/auth/login
  → Reçoit {login, password} du formulaire React
  → Cherche l'utilisateur dans MongoDB par son login
  → Compare le mot de passe avec bcrypt.compare() (hash vs saisie)
  → Vérifie le statut : si 'pending' → accès refusé (403), si 'refused' → 403
  → Si tout est bon : crée req.session.user avec les infos de l'utilisateur
  → Retourne les infos au client
  POURQUOI : C'est la porte d'entrée du site. Sans ça, personne ne peut
  accéder au forum.

POST /api/auth/logout
  → Détruit la session côté serveur avec req.session.destroy()
  → Efface le cookie côté client avec res.clearCookie()
  → Les deux sont nécessaires pour une déconnexion complète
  POURQUOI : Sécurité. Sans déconnexion côté serveur, la session resterait
  active même après fermeture du navigateur.

POST /api/auth/signup
  → Valide que tous les champs sont présents
  → Vérifie que le login n'est pas déjà pris (findOne)
  → Hashe le mot de passe
  → Insère l'utilisateur avec status: 'pending'
  → Retourne 201 Created
  POURQUOI : Le statut 'pending' est essentiel. Un nouveau membre ne peut
  pas accéder directement au forum. Un admin doit valider son compte.

GET /api/auth/me
  → Vérifie si req.session.user existe
  → Si oui, retourne les infos → le client React sait que l'utilisateur est
    déjà connecté (session persistée depuis une visite précédente)
  POURQUOI : Quand l'utilisateur recharge la page, React perd son état.
  Cette route permet de restaurer la session sans redemander le mot de passe.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

RÔLE : Gérer tous les messages — forum, commentaires, privés, likes, signalements, recherche.

C'est le fichier le plus important en volume car les messages sont au cœur
du site. Il gère 11 routes différentes.

FONCTION serializeMsg()
  Convertit les ObjectId MongoDB (type spécial) en strings JavaScript
  avant d'envoyer la réponse JSON. Sans ça, React reçoit des objets
  illisibles au lieu de simples chaînes de caractères pour les IDs.

GET /api/messages/public
  → Retourne les messages du forum ouvert sans vérifier la session
  → POURQUOI : Le forum est accessible en lecture même sans compte.
    ForumPublic.jsx l'utilise pour afficher le forum aux visiteurs.

GET /api/messages/private
  → Retourne TOUS les messages où l'utilisateur est auteur OU destinataire
  → $or: [{ authorId }, { recipientId }] → requête MongoDB avec opérateur "ou"
  → POURQUOI : Pour construire toutes les conversations privées de l'utilisateur.

GET /api/messages/search
  → Construit dynamiquement un filtre MongoDB selon les paramètres de l'URL
  → q → cherche dans le contenu avec $regex (expression régulière, insensible à la casse)
  → author → cherche par login avec $regex
  → from/to → filtre par date avec $gte (>=) et $lte (<=)
  → Les non-admins ne voient que le forum ouvert dans les résultats
  → POURQUOI : Permet une recherche multi-critères cumulable.

GET /api/messages/profile/:login
  → Retourne les messages publiés par un utilisateur spécifique
  → POURQUOI : Affiche les messages sur la page Profil.

ORDRE DES ROUTES IMPORTANT :
  Les routes /public, /private, /search, /profile/:login DOIVENT être
  définies AVANT /:id. Sinon Express interprèterait "search" comme un ID
  et essaierait de créer un ObjectId avec la chaîne "search" → erreur.

POST /api/messages
  → Crée un message dans le forum ouvert ou fermé
  → Vérifie que seuls les admins peuvent poster dans le forum fermé
  → parentId non null → c'est un commentaire sur un message existant
  → POURQUOI : Les commentaires et les messages principaux utilisent
    la même collection. La distinction se fait via parentId.

DELETE /api/messages/:id
  → Vérifie que l'auteur ou un admin fait la demande
  → Supprime le message ET ses commentaires (deleteMany avec $or)
  → POURQUOI : Si on supprime un message principal, ses réponses
    n'ont plus de sens. On les supprime aussi pour garder la cohérence.

POST /api/messages/:id/like
  → Vérifie si l'user a déjà liké (some() sur le tableau likes)
  → Si oui : $pull (retire l'ObjectId du tableau)
  → Si non : $push (ajoute l'ObjectId au tableau)
  → Toggle : un seul bouton gère like ET unlike
  → POURQUOI : Stocker les IDs des utilisateurs qui ont liké permet
    de savoir précisément qui a liké, éviter les doublons, et afficher
    l'état du bouton (liké ou non) pour chaque utilisateur.

POST /api/messages/:id/report
  → Vérifie qu'on n'a pas déjà signalé ce message
  → Ajoute {userId, reason, date} dans le tableau reports du message
  → POURQUOI : Les signalements sont stockés dans le message lui-même.
    Un admin pourrait lister les messages signalés en cherchant ceux
    dont reports.length > 0.

  → POURQUOI : L'admin voit les inscriptions en attente dans l'ordre

  → Retourne les informations publiques d'un utilisateur

  → POURQUOI : Quand un utilisateur inscrit se connecte, le serveur vérifie
    son status. S'il est 'active', il peut accéder au forum.

RÔLE : Configurer Vite — notamment le proxy vers le serveur.

Le proxy est crucial :
  server: {
    proxy: {
      '/api': { target: 'http://localhost:3000', changeOrigin: true }
    }
  }

SANS proxy : quand React fait api.get('/api/auth/me'), le navigateur
cherche http://localhost:5173/api/auth/me → qui n'existe pas sur le
serveur Vite.

AVEC proxy : Vite intercepte toute URL commençant par /api et la redirige
vers http://localhost:3000/api/auth/me → le serveur Express répond.

AVANTAGE : Les cookies de session fonctionnent correctement car du point de
vue du navigateur, tout vient du même "serveur" (localhost:5173).

RÔLE : Instance Axios centralisée avec la configuration commune.

  const api = axios.create({
    baseURL: '/api',
    withCredentials: true
  });

POURQUOI CE FICHIER :
  Sans lui, chaque composant devrait écrire la configuration Axios
  complète à chaque fois. Avec ce fichier, on importe "api" partout
  et on a automatiquement :
  - baseURL: '/api' → on écrit api.get('/auth/me') au lieu de
    axios.get('http://localhost:3000/api/auth/me')
  - withCredentials: true → le navigateur envoie automatiquement les
    cookies de session avec chaque requête. SANS ça, la session ne
    fonctionnerait pas du tout.

RÔLE : Bouton like/unlike avec compteur, indépendant pour chaque message.

STATE LOCAL :
  - liked → initialisé en vérifiant si currentUserId est dans initialLikes
  - count → initialisé à initialLikes.length

POURQUOI UN STATE LOCAL ET PAS DANS LE PARENT :
  Chaque bouton gère son propre état. Liker le message 1 ne doit pas
  déclencher un re-render de tous les autres messages. Le state local
  optimise les performances.

TOGGLE :
  Après la réponse du serveur { liked: bool, count: number }, on met à
  jour le state local → affichage immédiat sans recharger tous les messages.

RÔLE : Interface de messagerie privée style "chat".

CONSTRUCTION DES CONVERSATIONS :
  On récupère tous les messages privés de l'utilisateur (envoyés ET reçus).
  On en extrait la liste des interlocuteurs (Set pour éviter les doublons).
  En sélectionnant un interlocuteur, on filtre les messages pour n'afficher
  que ceux échangés entre eux deux.

STYLE "BULLES" :
  - mp-mine → bulle bleue à droite (messages envoyés par l'utilisateur)
  - mp-other → bulle grise à gauche (messages reçus)
  → Comme WhatsApp/Messenger

NOUVELLE CONVERSATION :
  Un champ de texte permet d'entrer le login d'un nouveau destinataire.
  Après envoi, la conversation apparaît dans la liste.

RÔLE : Interface admin pour valider ou refuser les inscriptions en attente.

N'est accessible et utile que pour les administrateurs.
Récupère GET /api/users/pending → liste des comptes en attente.

Pour chaque utilisateur :
  - Bouton vert "Valider" → PUT /api/users/:id/validate → status: 'active'
  - Bouton rouge "Refuser" → PUT /api/users/:id/refuse → status: 'refused'
  - Après l'action, l'utilisateur disparaît de la liste (filter côté client)

DOUBLE VÉRIFICATION CÔTÉ CLIENT :
  if (!user.isAdmin) return <erreur> → même si l'URL était accessible,
  le composant ne fait rien pour un non-admin.
